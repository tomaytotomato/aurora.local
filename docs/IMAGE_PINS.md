# Image pins — where they live, when they change

## The one-liner

Every package's image digests live in `packages/<pkg>/pins.env`. They are
refreshed by `scripts/pin.sh` and made real by `--apply`. Aurora's own
release process runs both.

## The full picture

**Q: When Aurora installs an app, which image does it pull?**

Two states are possible, and only one is honest:

1. **Pinned** — `packages/<pkg>/compose.yml` references `${IMAGE_<SVC>}`
   with a fallback of the moving tag; `packages/<pkg>/pins.env` defines
   `IMAGE_<SVC>=repo/name@sha256:…`. Compose interpolates the digest and
   Docker pulls exactly that image. Every box that installs the package
   at that release gets the same bits.

2. **Unpinned** — `compose.yml` references a moving tag (`v1`, `latest`,
   or nothing). Docker pulls whatever the tag points at *right now*. Two
   boxes installing the same day can get different images.

The doctrine (`ESSENCE.md`) says the boring decisions are already made:
Aurora chooses (1), by shipping a checked-in `pins.env` alongside every
package.

## Layout

Per package, two files carry the pinning story:

- `packages/<pkg>/compose.yml` — image references written as
  `${IMAGE_<SVC>:-repo/name:tag}`. The fallback is what runs on a
  developer clone without a `pins.env` (or on a `main` where pins have
  not been refreshed yet).
- `packages/<pkg>/pins.env` — a small shell-sourced file:

  ```
  # aurora.local / packages/notes/pins.env
  # Regenerated by scripts/pin.sh --refresh at 2026-08-29T20:00:00+01:00
  IMAGE_SILVERBULLET=ghcr.io/silverbulletmd/silverbullet@sha256:abcd…
  ```

  Never hand-edited. The header note is real: `scripts/pin.sh --refresh`
  rewrites the file wholesale from the current registry state.

The mechanism is deliberately outside `manifest.yml`. Manifests describe
the *shape* of a package (ports, dependencies, category, resource
requirements) — a fact people write and read. Pins describe the exact
byte-for-byte identity of an upstream image — a fact machines produce.
The two live side by side so the pin story never bloats the human file.

## The tool

`scripts/pin.sh` is the single seam. Three modes:

- `--check` (default). Walks every `packages/*/compose.yml`, resolves
  each image reference against the registry, compares to the current
  `pins.env`. Reports drift and exits 2 when it finds any; exits 0 when
  every service is on the pinned digest. Safe on a laptop.
- `--refresh`. Same walk, but rewrites `pins.env` per package with the
  resolved digests. Nothing else changes. This is where "today's digests"
  become "the pinned digests".
- `--apply`. After a refresh, rewrites each `compose.yml` `image:` line
  to reference `${IMAGE_<SVC>}` (if it does not already). Idempotent; a
  package that already references the variable is left alone.

The refresh + apply steps are ordered on purpose: refresh so the file on
disk is accurate, apply so `compose.yml` reads from it. A partial apply
leaves compose files that still reference moving tags, which is the state
being pinned away from.

## Aurora's release process

For every tagged Aurora release:

1. `./scripts/pin.sh --refresh` from a clean tree.
2. `./scripts/pin.sh --apply` (idempotent — no-op after the first release
   that ran it, but cheap to leave in).
3. `./scripts/verify.sh` (backend tests + vue-tsc + vitest +
   shellcheck).
4. Commit as one commit: `chore(pins): refresh image digests for vX.Y.Z`.

Between releases, `pin.sh --check` is available for anyone who wants to
see which images have moved. It is not a CI gate: a moving upstream tag
producing drift is normal, and turning that into a red PR would train
everyone to ignore the light.

## Why not per-manifest?

Two reasons the digest does not live in `manifest.yml`:

- **Frequency.** A manifest description or resource requirement changes
  rarely; a base-image digest changes on every upstream push. Mixing the
  two would fill the git log with pin-refresh noise obscuring real
  package changes.
- **Toolchain.** The manifest is human-authored; the pin file is
  machine-authored. Keeping them apart means `pin.sh --refresh` never
  touches a file a person is likely to be editing.

## Why not a dashboard button?

A "Pin these now" button was considered (see the C21 worksheet entry).
It is deliberately not shipped, for the same reason `pin.sh --check` is
not a PR gate: an operator hitting "pin these now" on a random Tuesday
would freeze that day's arbitrary upstream digests as the box's floor.
That's worse than not pinning at all, because it looks intentional
(they clicked a button) but isn't (they had no basis to pin at that
moment). The right time to pin is a release cut, and the right person to
run it is whoever is cutting the release — from the terminal.

## What the security posture rule says

`ImagePinRule` treats an un-digest-pinned image as a *low or medium*
finding, never HIGH, and its copy tells the household operator that
"Aurora pins these versions in its own releases and this entry
disappears when it does." That copy is enforced by a unit test
(`SecurityFindingsHouseholderCopyTests`) so any future edit to the rule
that reverts to shell-jargon copy fails the build.

The lower severity is not a workaround for a missing feature — it is
consistent with this document. The pin is real, it lives here, and it
updates on a release cut, not on the operator's schedule.
